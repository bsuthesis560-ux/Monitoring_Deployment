D1. No Rate Limiting on Login or Any Endpoint
The problem: The login endpoint can be called unlimited times. An attacker can run an automated script trying thousands of passwords per minute against any account.

How I would fix it:

Install the standard Express rate limiting library:


pnpm add express-rate-limit
Then apply different limits to different route categories. The login endpoint needs the tightest limit:


// artifacts/api-server/src/app.ts
import rateLimit from "express-rate-limit";

// Login: max 10 attempts per 15 minutes per IP
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 10,
  message: { error: "Too many login attempts. Please try again in 15 minutes." },
  standardHeaders: true,
  legacyHeaders: false,
});

// General API: max 200 requests per minute per IP
const apiLimiter = rateLimit({
  windowMs: 60 * 1000,
  max: 200,
  message: { error: "Too many requests. Please slow down." },
});

app.use("/api/auth/login", loginLimiter);
app.use("/api", apiLimiter);
This directly addresses brute-force attacks by enforcing a hard ceiling on how many login attempts can come from a single IP address within a time window.

D2. No Account Lockout After Failed Login Attempts
The problem: Even with rate limiting in place, it is good practice to lock an account at the account level (not just IP level) after too many failures, because an attacker may use distributed IPs.

How I would fix it:

Add two columns to the accounts table via a database migration:


// lib/db/src/schema/personnel.ts — add to accountsTable
failedLoginAttempts: integer("failed_login_attempts").notNull().default(0),
lockedUntil: timestamp("locked_until"),
Then update the login route to check and update these fields:


// In auth.ts POST /login
const MAX_ATTEMPTS = 5;
const LOCKOUT_MINUTES = 30;

// Check if account is currently locked
if (account.lockedUntil && account.lockedUntil > new Date()) {
  const minutesLeft = Math.ceil((account.lockedUntil.getTime() - Date.now()) / 60000);
  logger.warn({ username }, "Login attempt on locked account");
  res.status(423).json({
    error: `Account is locked. Try again in ${minutesLeft} minutes.`,
  });
  return;
}

const valid = await bcrypt.compare(password, account.passwordHash);

if (!valid) {
  const newAttempts = account.failedLoginAttempts + 1;
  const shouldLock = newAttempts >= MAX_ATTEMPTS;
  
  await db.update(accountsTable)
    .set({
      failedLoginAttempts: newAttempts,
      lockedUntil: shouldLock
        ? new Date(Date.now() + LOCKOUT_MINUTES * 60 * 1000)
        : account.lockedUntil,
    })
    .where(eq(accountsTable.id, account.id));

  res.status(401).json({ error: "Invalid username or password" });
  return;
}

// On successful login, reset the counter
await db.update(accountsTable)
  .set({ failedLoginAttempts: 0, lockedUntil: null })
  .where(eq(accountsTable.id, account.id));
This means after 5 failed attempts, an account is locked for 30 minutes regardless of how many IPs the attacker uses.

D3. No Dedicated Security Event Logging
The problem: HTTP logs show status codes but not security-meaningful context like which username failed to log in, from which IP, or what admin action was performed.

How I would fix it:

Create a dedicated security logger that writes structured entries alongside the regular HTTP log. Using the existing Pino instance, I would add a specific security log function:


// artifacts/api-server/src/lib/security-log.ts
import { logger } from "./logger";

type SecurityEvent =
  | "LOGIN_SUCCESS" | "LOGIN_FAILED" | "LOGIN_LOCKED"
  | "LOGOUT"
  | "ACCOUNT_CREATED" | "ACCOUNT_UPDATED" | "ACCOUNT_DELETED"
  | "PERSONNEL_CREATED" | "PERSONNEL_UPDATED" | "PERSONNEL_DELETED"
  | "INVALID_API_KEY";

export function securityLog(
  event: SecurityEvent,
  context: { username?: string; ip?: string; targetId?: number; performedBy?: number; detail?: string }
) {
  logger.warn({ security: true, event, ...context }, `[SECURITY] ${event}`);
}
Then call it in every sensitive route:


// In auth.ts — failed login
securityLog("LOGIN_FAILED", { username, ip: req.ip });

// In auth.ts — successful login
securityLog("LOGIN_SUCCESS", { username: account.username, ip: req.ip });

// In accounts.ts — account deleted
securityLog("ACCOUNT_DELETED", { targetId: id, performedBy: adminAccount.id, ip: req.ip });

// In personnel.ts — personnel deleted
securityLog("PERSONNEL_DELETED", { targetId: id, performedBy: adminAccount.id, ip: req.ip });
This gives a searchable, structured log trail of every security-relevant event in the system.

D4. No Audit Trail for Administrative Actions
The problem: There is no record of who changed what and when. If a personnel record is deleted, there is no way to know which admin did it.

How I would fix it:

Add an audit_logs table to the database schema:


// lib/db/src/schema/personnel.ts
export const auditLogsTable = pgTable("audit_logs", {
  id:          serial("id").primaryKey(),
  performedBy: integer("performed_by"),          // account ID of the admin
  action:      text("action").notNull(),           // e.g. "DELETE_PERSONNEL"
  targetType:  text("target_type").notNull(),      // e.g. "personnel", "account"
  targetId:    integer("target_id"),
  detail:      text("detail"),                     // JSON string with before/after snapshot
  ip:          text("ip"),
  timestamp:   timestamp("timestamp").defaultNow().notNull(),
});
Then write a helper that inserts an audit record and call it in every admin route after a successful action:


// In personnel.ts — after successful delete
await db.insert(auditLogsTable).values({
  performedBy: adminAccountId,
  action: "DELETE_PERSONNEL",
  targetType: "personnel",
  targetId: id,
  detail: JSON.stringify({ employeeId: existing.employeeId, name: `${existing.firstName} ${existing.lastName}` }),
  ip: req.ip,
});
This creates a permanent, queryable history of every admin action that can be reviewed for accountability or incident response.

D5. No Backup for Personnel Records
The problem: If the personnel table or personnel_photos table is corrupted or accidentally deleted, there is no recovery path.

How I would fix it:

Following the same pattern already used for accounts, I would add an automatic personnel backup triggered on every create, update, and delete:


// artifacts/api-server/src/lib/backup.ts
import { db, personnelTable, personnelPhotosTable } from "@workspace/db";
import fs from "fs";
import path from "path";

const BACKUP_DIR = path.resolve(process.cwd(), "personnel_backup");

export async function writePersonnelBackup(): Promise<void> {
  try {
    const rows = await db.select().from(personnelTable).orderBy(personnelTable.id);

    const header = ["ID", "Employee ID", "Last Name", "First Name", "Middle Initial", "Department", "Position", "Created At"].join(",");
    const lines = rows.map((r) =>
      [r.id, r.employeeId, `"${r.lastName}"`, `"${r.firstName}"`, r.middleInitial ?? "", `"${r.department}"`, `"${r.position}"`, r.createdAt.toISOString()].join(",")
    );

    const csv = [
      `# Personnel Backup — Generated: ${new Date().toISOString()}`,
      `# Total records: ${rows.length}`,
      header,
      ...lines,
    ].join("\n");

    if (!fs.existsSync(BACKUP_DIR)) fs.mkdirSync(BACKUP_DIR, { recursive: true });
    fs.writeFileSync(path.join(BACKUP_DIR, "personnel_backup.csv"), csv, "utf-8");
  } catch (err) {
    console.error("[PersonnelBackup] Failed:", err);
  }
}
Call void writePersonnelBackup() at the end of every POST, PUT, and DELETE handler in personnel.ts, matching exactly how writeAccountBackup() is already used in accounts.ts.

D6. No Backup for Attendance Logs
The problem: All attendance history lives only in the database. There is no secondary copy for recovery or reporting.

How I would fix it:

Add a scheduled daily export of attendance logs to a CSV file. Since the system runs on Node.js, I would use a lightweight scheduler:


pnpm add node-cron

// artifacts/api-server/src/lib/backup.ts — add alongside personnel backup
import cron from "node-cron";

export async function writeAttendanceBackup(): Promise<void> {
  const ATTENDANCE_BACKUP_DIR = path.resolve(process.cwd(), "attendance_backup");
  try {
    const logs = await db.select().from(attendanceLogsTable).orderBy(attendanceLogsTable.timestamp);
    const header = ["ID", "Employee ID", "Name", "Department", "Position", "Log Type", "Timestamp"].join(",");
    const lines = logs.map((l) =>
      [l.id, l.employeeId, `"${l.name}"`, `"${l.department}"`, `"${l.position}"`, l.logType, l.timestamp.toISOString()].join(",")
    );
    const csv = [
      `# Attendance Log Backup — Generated: ${new Date().toISOString()}`,
      header,
      ...lines
    ].join("\n");

    if (!fs.existsSync(ATTENDANCE_BACKUP_DIR)) fs.mkdirSync(ATTENDANCE_BACKUP_DIR, { recursive: true });
    const filename = `attendance_${new Date().toISOString().split("T")[0]}.csv`;
    fs.writeFileSync(path.join(ATTENDANCE_BACKUP_DIR, filename), csv, "utf-8");
  } catch (err) {
    console.error("[AttendanceBackup] Failed:", err);
  }
}

// Schedule daily backup at midnight
export function startBackupScheduler() {
  cron.schedule("0 0 * * *", () => {
    void writeAttendanceBackup();
  });
}
Then call startBackupScheduler() once when the server starts in index.ts. This produces a dated CSV file every night, so even if the database fails, attendance history is recoverable from the most recent nightly file.

D7. No HTTP-to-HTTPS Redirect in Application Code
The problem: The system relies on Replit's platform to enforce HTTPS. If ever deployed to a different environment (a VPS, a Docker container, etc.) without a reverse proxy enforcing HTTPS, the application would accept plain HTTP connections and cookies marked secure would not be set.

How I would fix it:

Add a simple middleware that detects non-HTTPS connections and redirects them. In production behind Replit, the x-forwarded-proto header indicates the original protocol:


// artifacts/api-server/src/app.ts
if (process.env.NODE_ENV === "production") {
  app.set("trust proxy", 1); // trust first proxy (Replit's load balancer)

  app.use((req, res, next) => {
    if (req.headers["x-forwarded-proto"] !== "https") {
      return res.redirect(301, `https://${req.headers.host}${req.url}`);
    }
    next();
  });
}
trust proxy is needed so Express correctly reads the x-forwarded-proto header set by Replit's reverse proxy. Without it, the header is ignored for security reasons. This ensures that even if someone accesses the plain HTTP URL, they are immediately redirected to HTTPS.
