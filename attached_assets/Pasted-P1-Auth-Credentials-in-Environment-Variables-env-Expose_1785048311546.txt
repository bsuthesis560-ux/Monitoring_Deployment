P1. Auth Credentials in Environment Variables — .env Exposed in Repository
The problem: The backend code correctly reads secrets from process.env, but the actual .env file containing live credentials sits inside the repository and is not excluded by .gitignore.

How I would fix it:

First, add .env to .gitignore immediately so it is never committed again:


# .gitignore — add these lines
.env
.env.local
.env.production
*.env
Then create an .env.example file as a safe template that documents what values are needed without including the real values. Other developers clone the repo, copy .env.example to .env, and fill in their own credentials:


# services/facial-recognition/.env.example
API_URL=https://your-deployment-url.replit.app
API_KEY=your-facial-recognition-api-key-here

CAM1_NAME=Camera 1
CAM1_IP=192.168.x.x
CAM1_USER=admin
CAM1_PASS=your-camera-password
CAM1_PORT=554
CAM1_STREAM_PATH=/Streaming/Channels/101
Since the .env was previously committed, the credentials are already in git history. Those credentials must be rotated immediately — change the API key value and camera passwords — because removing a file from .gitignore does not erase it from git history. Anyone who cloned the repo before the fix still has those credentials.

P2. API Keys Read from Environment Variable — Same Root Cause as P1
The problem: This is the same issue. The code reads API_KEY correctly from process.env, but the actual key value bsu-tneu-facerec-2025 is visible inside the committed .env file.

How I would fix it:

Fixing P1 above resolves this automatically once the .env is gitignored. Additionally, I would generate a stronger API key. The current key bsu-tneu-facerec-2025 is a human-readable string that follows a predictable pattern. A professional-grade API key should be a cryptographically random string:


// Run this once to generate a strong key
import crypto from "crypto";
console.log(crypto.randomBytes(32).toString("hex"));
// Output example: a3f9c2d71e804b56a9f3c18d72e0b4a9c5d12e7f8a4b6c3d1e2f9a8b7c6d5e4
Use that generated value as FACIAL_RECOGNITION_API_KEY in the real .env and rotate it from the old predictable value.

P3. Request Validation — No Zod Middleware, No Length Limits, No Format Patterns
The problem: Zod schemas exist in lib/api-zod/ but they are generated types for the client, not enforced as backend middleware. Each route does manual checks like if (!lastName || !firstName) but does nothing about field length, format, or unexpected extra fields.

How I would fix it:

I would write a reusable validation middleware that accepts a Zod schema and applies it to the request body. Then define proper schemas with length and format constraints for each route:


// artifacts/api-server/src/middleware/validate.ts
import { z, ZodSchema } from "zod";
import type { Request, Response, NextFunction } from "express";

export function validate(schema: ZodSchema) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      res.status(400).json({
        error: "Validation failed",
        details: result.error.flatten().fieldErrors,
      });
      return;
    }
    req.body = result.data; // replace with parsed/stripped data
    next();
  };
}
Then define strict schemas directly in the routes:


// In personnel.ts
const createPersonnelSchema = z.object({
  lastName:      z.string().min(1).max(100).trim(),
  firstName:     z.string().min(1).max(100).trim(),
  middleInitial: z.string().max(5).trim().optional(),
  employeeId:    z.string().min(1).max(50).regex(/^[A-Z0-9\-]+$/i),
  department:    z.enum(["CET Faculty", "ICT", "ADMIN", "HR"]),
  position:      z.string().min(1).max(100).trim(),
  photoUrl:      z.string().optional(),
  photos:        z.object({
    front: z.string().optional(),
    left:  z.string().optional(),
    right: z.string().optional(),
    top:   z.string().optional(),
  }).optional(),
});

router.post("/", validate(createPersonnelSchema), async (req, res) => { ... });
This approach eliminates the scattered manual if (!field) checks, enforces maximum lengths, and strips unexpected fields automatically.

P4. Input Validation and Sanitization — No Sanitization Library, No Length Limits
The problem: React's JSX auto-escaping protects the frontend render layer, but there is no server-side sanitization of string inputs before they enter the database. Unusually long strings, special characters designed to break output, or whitespace-only values can all be stored.

How I would fix it:

The Zod schema approach from P3 already handles length limits. For additional sanitization I would add .trim() to all string fields in the Zod schemas (already shown above) so leading/trailing whitespace is stripped before storage. I would also install a lightweight sanitization utility for any fields that might be rendered as HTML in a document context (such as PDF exports):


pnpm add dompurify
pnpm add -D @types/dompurify
Then sanitize name fields before they go into a PDF:


// In pdf-export.ts
import DOMPurify from "dompurify";
const safeName = DOMPurify.sanitize(personnel.firstName);
On the backend, for the attendance log route, I would also sanitize the employeeId field before the database lookup to prevent any injection attempts through that vector, even though parameterized queries already protect the SQL layer.

P5. File Size Validation — No Per-File Limit, No MIME Verification
The problem: The 10MB Express body limit is the only defense. A user could submit a request with multiple photos each close to 3MB, or submit a photo with a forged MIME type.

How I would fix it:

I would add a dedicated photo validation function that is called before inserting any photo into the database:


// artifacts/api-server/src/lib/validate-photo.ts
const ALLOWED_MIME_TYPES = ["image/jpeg", "image/png"];
const MAX_PHOTO_BYTES = 2 * 1024 * 1024; // 2MB per photo

export function validatePhoto(dataUri: string): { valid: boolean; error?: string } {
  // Must start with data: URI scheme
  if (!dataUri.startsWith("data:")) {
    return { valid: false, error: "Invalid photo format" };
  }

  // Extract MIME type from data URI header
  const mimeMatch = dataUri.match(/^data:([^;]+);base64,/);
  if (!mimeMatch) {
    return { valid: false, error: "Malformed data URI" };
  }

  const mimeType = mimeMatch[1].toLowerCase();
  if (!ALLOWED_MIME_TYPES.includes(mimeType)) {
    return { valid: false, error: `File type '${mimeType}' is not allowed. Only JPEG and PNG are accepted.` };
  }

  // Check decoded size
  const base64Data = dataUri.split(",")[1];
  const byteSize = Math.ceil((base64Data.length * 3) / 4);
  if (byteSize > MAX_PHOTO_BYTES) {
    return { valid: false, error: `Photo exceeds maximum size of 2MB` };
  }

  return { valid: true };
}
Then call this in the personnel route before any database insert, for every photo view that is submitted.

P6. File Format Not Restricted to JPG/JPEG/PNG — Only Checks startsWith("data:image")
The problem: data:image/svg+xml and data:image/gif both start with "data:image" and would pass the current check. SVG images can contain embedded <script> tags and are a known XSS vector when rendered in a browser.

How I would fix it:

The validatePhoto() function defined in P5 above solves this directly by extracting and checking the exact MIME type against an allowlist of ["image/jpeg", "image/png"]. Apply that function in three places:

In personnel.ts before inserting photos on create and update
In personnel.ts before inserting photoUrl (legacy single-photo field)
In logs.ts inside the personnel-photos endpoint, change the filter condition from startsWith("data:image") to use the validated MIME type check
This ensures that regardless of how a photo arrives in the system — through registration, update, or the facial recognition endpoint — only genuine JPEG and PNG data URIs are accepted.
